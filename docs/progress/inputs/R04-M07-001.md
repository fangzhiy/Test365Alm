三、需求身份、修订和数据库

- requirement_revision：独立修订 ID、需求 ID、
  修订号、完整内容快照、作者稳定 ID、创建时间。

具体物理字段在 ADR 中记录，但必须满足：

1. 需求稳定 ID 与显示编号分开，创建后不因编辑而改变。
2. 显示编号由服务端安全分配，项目内唯一；

4. 复合外键保证当前修订属于同一需求和同一项目，
   不能把项目 A 的需求指向项目 B 的修订。
5. 创建产生第一版；实际内容修改产生新修订，
   历史修订不可 UPDATE/DELETE。
6. 编辑不覆盖旧正文，历史作者引用 principal 稳定 ID。
7. 同内容且前置版本有效的请求可返回当前版本，
   不重复增加修订、审计或业务事件；在契约中固定行为。
8. 新增 Flyway 迁移，不改写已经执行的 V1—V6。

四、权限要区分“需求编辑”和“项目管理”

本轮固定策略：
- 有效 PROJECT_ADMIN：读取、创建、编辑需求、读取历史。
- 有效 PROJECT_MEMBER：读取、创建、编辑需求、读取历史。
- 有效 PROJECT_VIEWER：读取需求及历史，不得创建或编辑。
- 只有 TENANT_ADMIN 或站点管理身份、但没有项目成员关系：
  不自动获得需求访问权。
- 匿名、停用主体、失效租户成员、撤销项目成员：
  不得访问对应需求。

将 requirement:read/create:update 等动作名称统一冻结；
可使用 requirement:read、requirement:create、
requirement:update、requirement:history:read 这一组。
不要误把需求写权限等同于 project:manage-members。

操作者只来自服务端已认证会话。
客户端传入的项目、需求和修订 ID 只是选择条件，不是授权证明。
项目列表、需求搜索、历史及数量统计都要遵守同一授权。

复用当前受限 runtime 数据源和事务上下文机制，
新表增加对应 RLS，迁移账户不能用于普通业务。

注意现有审计写策略可能只允许管理员：
需要支持 PROJECT_MEMBER 的合法需求事件时，
只扩展到被授权的需求动作和目标；
不能顺便允许普通成员写成员管理或租户管理事件。

权限变化提交后，旧会话下一次需求请求使用最新数据库授权。
无需先调用 /me 才能拒绝失效用户。

五、接口与并发规则

实现并更新契约：

POST  /api/v1/projects/{projectId}/requirements
GET   /api/v1/projects/{projectId}/requirements
GET   /api/v1/projects/{projectId}/requirements/{requirementId}
PATCH /api/v1/projects/{projectId}/requirements/{requirementId}
GET   /api/v1/projects/{projectId}/requirements/{requirementId}/revisions
GET   /api/v1/projects/{projectId}/requirements/{requirementId}/revisions/{revisionId}

要求：

1. 列表有默认页大小和最大上限，固定排序白名单；
   支持标题/编号的简单参数化查询，不开放任意 SQL。
2. GET 详情返回版本标识和 ETag。
3. PATCH 必须使用从详情获得的具体 If-Match 版本；
   缺失前置条件拒绝，陈旧版本返回 412。
   不允许通过省略版本或使用通配符无条件覆盖。
4. 先校验权限，再返回版本冲突详情，
   避免无权用户通过错误响应读取目标信息。
5. 两个真实事务基于同一版本编辑：
   只允许一次更新成功，另一次得到明确的陈旧版本结果。
6. 401/403/404/412 使用现有结构化 JSON 错误风格。
7. 写入保留同源 Cookie、CSRF、输入长度与类型校验。
8. 发布接口不接收客户端自定的作者、创建时间、
   当前修订指针或权限字段。

创建接口实现有限范围的重复提交保护：
- 使用已有幂等机制；没有时，为本接口实现持久化幂等记录。
- 键按主体、项目、路由作用域隔离。
- 同一键和相同请求，不重复创建需求/修订/审计/事件。
- 同一键不同请求体返回 409。
- 并发同键也只能创建一份。
- 重放结果前重新检查当前权限。
- 明确保留期限，不扩建通用任务或消息平台。
