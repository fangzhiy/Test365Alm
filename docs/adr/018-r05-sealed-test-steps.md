# ADR-018：保存后封存手工测试步骤集合

## 状态

已接受（R05-M08-001-FIX01 范围）；不代表完整 M08 已完成。

## 背景

V10 将步骤作为修订快照写入，并通过受限 runtime 的 RLS/GRANT 阻止常规更新、删除
和清空。但仅有 INSERT 边界时，拥有合法项目写权限的主体仍可能向已保存的历史或当前
修订追加一个新的、归属正确的步骤。这样的追加会改变不可变历史和幂等重放结果。

## 决策

1. V11 为 `test_revision` 增加 `sealed_at`。应用创建或追加修订时先在同一事务写入
   完整步骤快照，再通过只允许 `NULL → 非 NULL` 的列级更新策略封存修订。运行时不能
   重新打开已经封存的修订；V10 既有行升级时使用其 `created_at` 作为可追踪的封存时间。
2. `test_step` 的 INSERT 策略调用固定 `search_path=public` 的 `SECURITY DEFINER`
   只读函数：对存在但已封存的精确修订在 RLS 边界拒绝；不存在的归属仍沿用复合外键
   约束的错误路径。函数不执行迁移、修复或清理，也不授予任意身份绕过权限。
3. 受限 runtime 仅获得 `test_revision.sealed_at` 的 UPDATE 列权限，不能修改修订正文、
   身份或封存时间；步骤集合的 UPDATE/DELETE/TRUNCATE 继续没有 runtime 权限。正常的
   新修订仍可在封存前完成完整步骤写入，旧 `step_key` 可在新修订中合法保留。
4. 真实 PostgreSQL 测试使用合法 `PROJECT_MEMBER` 和隔离 Testcontainers，分别尝试向
   已保存的历史与当前修订追加新步骤，断言拒绝 SQL 状态及业务、审计、Outbox、幂等和
   历史快照均未改变。迁移升级测试从 V9 执行到 V11；正式迁移编号之后的故意失败探针
   使用 V12。

## 后果与未覆盖

封存边界解决的是已保存步骤集合的追加/修改边界，不是完整 M08 发布审批或执行模型。
V10 既有封存时间只能追溯到创建时间，不能声称精确记录历史封存时刻。完整测试树、
参数、附件、执行、结果和需求关联继续按开发状态保留未实现。
