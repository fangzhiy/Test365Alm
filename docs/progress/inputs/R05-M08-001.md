三、先冻结契约和数据身份

至少分别建模：
- test_case：稳定用例身份、项目内显示编号、
  当前修订指针、并发版本和创建信息。
- test_revision：独立修订 ID、所属用例、
  修订号、标题、说明、前置条件、作者与时间。
- test_step：所属用例与修订、稳定 step_key、
  顺序值、操作内容、预期结果。

具体字段、长度、步骤数量上限、空值和错误码写入契约。
可允许没有步骤的初始用例，但明确它只是测试定义，
不能因此声称它已可执行或已经运行。

必须满足：

1. 稳定 UUID 与显示编号分开。
   显示编号由服务端并发安全分配，项目内唯一，
   不使用无锁 MAX(number)+1。
   可使用 TC- 前缀；编号空隙允许但不得重复。

2. 当前修订外键必须包括同租户、同项目、同用例归属，
   不能把用例 A 指向同项目用例 B 的修订。

3. 步骤必须引用同租户、同项目、同用例的修订。
   step_key 与 ordinal 分开，不能用数组下标充当稳定身份。

4. 创建时步骤稳定键由服务端生成。
   修改、调序已有步骤保留其稳定键；
   新步骤分配新键，移除步骤只影响新修订。
   不接受其他用例的 step_key 冒充当前用例已有步骤。

5. 编辑保存产生完整的新修订及步骤快照。
   旧修订的正文、顺序、作者和时间不得原地修改。

6. 相同用例修订内 step_key 和顺序值不得重复；
   同时拒绝重复键、非法顺序和不属于该用例的步骤。

7. 内容和顺序没有变化且版本有效时，
   不重复增加修订、审计或事件。
   前置版本过期仍按契约处理，不能借“无变化”绕过。

8. 历史修订和历史步骤对 runtime 禁止
   UPDATE、DELETE、TRUNCATE。
   owner 仅用于迁移、测试夹具和结果核验。

通过新增 Flyway 迁移实现。
当前正式基线至 V9；开始时重新检查真实迁移列表。
不得改写已执行 V1—V9，也不得清库替代升级验证。

若新增正式 V10 等迁移，
同步调整当前“故意失败 V10”的探针，
确保故障来自测试 SQL，而不是迁移版本号重复。

四、接口与版本前置条件

沿用 M08 的 tests 路径，至少实现：

POST /api/v1/projects/{projectId}/tests

GET  /api/v1/projects/{projectId}/tests/{testId}

GET  /api/v1/projects/{projectId}/tests/{testId}/revisions
GET  /api/v1/projects/{projectId}/tests/{testId}/revisions/{revisionId}

创建请求包含用例字段和有序步骤集合。
追加修订请求提交完整编辑快照；
服务端负责生成新修订，而不是让客户端直接写历史表。

要求：

1. 详情返回真实 ETag。
   追加修订使用当前用例版本作为明确的前置条件，
   将 If-Match 对应的资源版本语义写入契约。

2. 缺失前置条件拒绝，陈旧版本返回 412。
   沿用已冻结的单个强 ETag 格式，不接受裸数字、
   弱标签、通配符或省略版本来覆盖。

3. 先授权，再返回涉及目标版本的响应，
   无权用户不能通过冲突信息获得内容或版本。

4. 两个独立事务基于同一版本保存，
   只能一个成功，另一个得到明确的陈旧版本错误。
   失败方不得留下半份步骤或多余事件。

5. 创建和追加修订都具备持久化重复提交保护。
   相同作用域、键和内容重放同一结果；
   同键不同内容返回 409；
   重放前重新检查当前权限。

6. 摘要包含有意义的字段、步骤顺序、步骤稳定键
   及适用的前置版本，使用无歧义编码。
   新步骤键的服务端生成不能导致同一请求重试失配。

7. 重放返回原操作的冻结结果，
   不返回后来被修改的最新用例冒充原响应。
   保留期限与过期行为明确，不新建通用调度平台。

8. 列表提供有界分页和固定稳定排序；
   支持简单标题/编号查询即可，查询参数化。
   不开放任意排序字段、SQL 或无限返回全部记录。

9. 明确拒绝未知字段、错误 JSON 类型、
   不支持的类型、跨范围引用、超限字段和非法步骤。
   不静默忽略作者、租户、权限、当前修订等受控字段。

10. 保留真实会话、同源 Cookie 和 CSRF。
    结构化错误沿用项目既有风格。
