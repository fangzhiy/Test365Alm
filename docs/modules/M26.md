# M26 电子签名、审计与证据保留

阶段：P2/P3。责任角色：安全 / 合规负责人。当前状态：PLANNED。

## 输入与依赖

完整模块依赖：M03、M05、M07、M09、M14。这里表示最终集成依赖；预研或早期最小切片可先行。开始具体 Issue 前，须声明所依赖接口、数据约束和切片版本，不能把尚未开发的依赖假装可用。

准备签批范围、授权样本、角色矩阵和适用基线；将未满足条件登记为 BLOCKED，不伪造输入。

领域对象：`signature_policy`、`signature_request`、`signature_record`、`evidence_hash`、`audit_event`、`retention_policy`。

- `POST /api/v1/projects/{projectId}/signature-requests`
- `POST /api/v1/projects/{projectId}/signature-requests/{requestId}/sign`
- `GET /api/v1/projects/{projectId}/evidence-bundles/{bundleId}`

## 按顺序实施

### M26-T01

先由业务和合规人员确定签名含义、签批对象、身份确认、双人复核、保留期限和适用要求；产品实现不等同于自动获得监管认证。

### M26-T02

签名绑定对象修订、附件清单和规范化内容哈希；使用再认证与挑战 nonce，验证挑战绑定主体及对象，拒绝重放。

### M26-T03

保存签名人稳定身份、意义、时间来源、认证强度、策略版本与服务端证据；服务端签封用于完整性保护，不冒称用户本人持有证书作出的数字签名。

### M26-T04

对象变化产生新修订，原签名仍对应旧内容；撤销签名以追加事件记录原因及授权人，不能删除原记录。

### M26-T05

审计事件写入追加通道并定期对外签封或受控不可变存储；哈希链本身不能阻止有数据库管理权限的人整体重写，需独立信任边界。

### M26-T06

历史迁入签名保留源系统证明和验证状态；新系统不得生成当年时间的伪签名，证据包提供离线验证说明。

## 验收与负向测试

**M26-AC01：** 签名后修改正文或附件会造成新版本，旧签名不被自动沿用。

**M26-AC02：** 重放签名挑战被拒绝。

**M26-AC03：** 管理员不能通过普通业务接口修改或删除审计历史。

**M26-AC04：** 迁入签名显示原始来源与可验证程度，不伪装成本站原生签署。

**M26-AC05：** 证据包内容被篡改后校验失败，可定位受影响对象。
