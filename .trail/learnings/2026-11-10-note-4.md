## Decided
A missing business execution time in a pre-upgrade PASS/FAIL/BLOCKED step remains unknown when later text is corrected. Only a server-observed transition from NOT_RUN to a concluded state establishes the first execution time; later saves retain it. Save time and execution time have different meanings.

## Tried and ruled out
Setting an execution time whenever a concluded row has a null timestamp would date historical work at a later text correction. Backfilling from updated_at was also rejected because that records persistence, not necessarily execution. Old frozen idempotency responses retain their old shape instead of gaining newly allocated evidence identifiers.

## Watch out
Historical migration tests must verify their original intermediate target first, then migrate to the current schema before invoking current production services. Compare all original fields, explicitly excluding only newly added columns, and check new fields separately. Integration regressions are written but not yet run at this checkpoint.

In the code:
V24 execution_step_clock uses the OLD.conclusion=NOT_RUN transition. ManualExecutionMigrationUpgradeIT keeps V13/V14 to V16 and V16 to V17 checks, then exercises current runtime; its V22 to V24 fixture includes an already concluded active step with no execution timestamp.
