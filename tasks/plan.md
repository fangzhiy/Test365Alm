# Test365Alm P0 六周执行计划

## 目标与边界

P0 是启动、范围冻结和高风险验证阶段，对应 `S01-S03 / W01-W06`。它的出口是 G0 评审包：管理层可以基于证据决定继续、调整或暂停后续投入。P0 不把文档、脚手架或概念验证当作已完成的 ALM 产品，也不承诺目标版本、旧客户端或插件的零修改兼容。

P0 必须回答四个问题：

1. 实际目标环境、版本、Edition、扩展、旧客户端和授权样本是什么。
2. 三类脱敏项目中的历史版本、关系、附件、运行记录和签名能否合法取得，哪些存在缺口。
3. 基线固定、运行 manifest、REST/OTA/COM/VBScript 和迁移重跑等高风险行为是否有可复跑证据。
4. 后续工程的范围、架构、预算、责任人、关键路径和阻塞处理是否足以放行 G0。

依据：`docs/02-technical-implementation.md` 第 6 节、`planning/sprints.csv` 的 S01-S03、`planning/wbs.csv` 的 M01/M02/M19/M24/M25/M29、`planning/risk-register.csv`、`planning/compatibility-matrix.csv`、`planning/e2e-cases.csv` 的 E2E-002/E2E-003/E2E-005/E2E-006/E2E-016/E2E-019，以及 `contracts/domain-model.md` 和 `contracts/runner-protocol.md`。

## P0 工作原则

- 所有目标行为都要绑定来源、样本、构建或运行证据；`NOT_RUN` 不得改成“通过”而没有记录。
- 未知项保持 `OPEN`，并登记负责人、影响、截止闸门和关闭证据；不能用“未提供”把范围悄悄排除。
- 业务实体采用稳定身份与不可变修订分离；运行创建时固定 manifest，不能读取当前 `latest`。
- 业务写入、审计意图和 outbox 事件必须规划为同一事务；兼容入口不能绕过业务内核。
- P0 先做高风险、低成本验证。可并行的工作流共享只读样本和契约，涉及同一 schema、版本号或范围矩阵的写入必须由单一负责人合并。
- 未经授权的生产数据、真实凭据、厂商专有代码和安装包不得进入仓库；证据库只保存受控引用、哈希和访问记录。

## G0 放行标准

G0 只能在以下条件全部满足或被正式记录为“调整/暂停”后结束：

- 目标版本、补丁、Edition、扩展、客户端位数、数据库和认证方式有授权证据；未知项均有负责人、截止闸门和影响（对应 M01-AC01、M01-AC04）。
- 普通、强定制、大容量三个脱敏样本有访问审批、数量清单、哈希、来源和保留策略（M01-AC02）。
- 至少 10 个 REST 调用、3 个 OTA 程序、3 段 VBScript、1 个基线、1 个离线包有原始轨迹或明确无法取得的记录；零修改、需改写、不支持、未测试四类状态可追溯（M01-AC03、M24-AC01～05、M25-AC01～05）。
- 基线/manifest PoC 证明并发修改不会混入不同修订；运行读取固定快照；失败原因可解释（E2E-005、E2E-006 的 P0 证据，后续由 M14/M09 完整实现）。
- 迁移 PoC 可中断、续传、重复重跑；实体、关系和附件不重复；每个源对象有迁移、隔离、保留或不支持去向（M19-AC01～04）。无法验证的历史签名、作者、时区和附件必须列入缺口。
- 新开发机可按 README 构建健康检查并得到一致版本；明文凭据扫描、架构依赖检查、数据库迁移和失败发布保护有可复跑结果（M02-AC01～05）。
- 数据/API/权限/状态机/审计/outbox 设计有 ADR 和 review 记录，数据库演进顺序不冲突，后续任务有范围 ID、验收 ID 和证据路径。
- 独立 QA 复跑结果与原执行者一致；所有失败都有缺陷或阻断项，不能用平均通过率抵消关键未完成项。
- 阶段额度、团队容量、专项人才、外部环境和每个高风险的关闭条件已确认；预算仍是规划假设，不得宣传成已批准合同金额。
- 管理层签批的是范围和阶段额度，而不是“产品完成”（M01-AC05）。

G0 输出必须至少包含：会议纪要、签批范围、版本/兼容矩阵、黄金样本索引、迁移缺口报告、ADR/API/数据基线、风险登记、预算与容量表、P1 前 13 个迭代的任务索引、阻断清单和 QA 证据索引。

## 阻塞项与升级规则

| 阻塞 ID | 触发条件 | 影响 | 责任人 | 升级时点 | 解除证据/决策 |
|---|---|---|---|---|---|
| B01 | 目标版本、Edition 或扩展未确认 | P0-02/P0-06/P0-07 无法冻结范围；兼容声明只能保持 `OPEN` | 产品负责人 | W01 末；W02 仍无答复升级 G0 | 版本和授权台账，或管理层接受调整范围 |
| B02 | 三类样本或其访问授权未取得 | P0-03/P0-08/P0-09/P0-12 无法证明迁移和历史一致性 | 业务验收人、迁移负责人 | W02 末 | 合法脱敏样本；否则只做接口设计并把迁移能力列为阻断项 |
| B03 | Windows VM、位数、SDK 或旧客户端不可用 | P0-07、M25/M24 证据缺失，不能宣称零修改兼容 | 兼容负责人、授权负责人 | W02 末 | 合法隔离实验室和安装授权；否则标记 `not-tested` 并调整 G0 目标 |
| B04 | REST/OTA/COM/脚本许可或分发路径不清 | 不能发布兼容组件或复制专有资产 | 授权负责人 | W04 末 | 法务/授权意见、独立实现边界、组件 SBOM 和分发限制 |
| B05 | 团队关键角色或预算未到位 | P0-10/P0-12 不能独立复核；后续排期不可信 | 项目负责人 | W02、W05 | 责任人名单、投入承诺、预算决议；否则进入“调整”或“暂停” |
| B06 | 基线、manifest 或迁移重放出现不可解释差异 | 数据模型和后续 P1 被阻断，不能靠 UI 演示绕过 | 架构师、迁移负责人 | W03 立即升级 | 修正模型并重复 PoC；仍失败则暂停扩展开发 |
| B07 | 发现跨租户越权、密钥泄露或高危漏洞 | 立即阻断构建/放行 | 安全负责人 | 发现即升级 | 修复、回归和独立 QA 证据；未关闭不得 G0 放行 |
| B08 | 依赖版本或构建不能在空机器复现 | 后续 CI、迁移和证据不可复核 | DevOps | W02 末 | 锁文件、镜像摘要、构建日志和回滚记录 |

阻塞项不以“暂时跳过”关闭。只能通过取得证据、批准范围调整、明确转为后续闸门，或暂停相关投资来结案；所有决定写入 G0 纪要。

## P0 完成定义与后续衔接

P0 任务完成必须有：范围或决策编号、责任人、输入样本/版本、实际执行日志、输出文件或链接、验收断言、独立复核和未解决差异。P0 结束后，P1 才能根据批准范围启动 M02/M03 及核心纵向切片；P0 未解决的兼容和迁移问题必须进入 G1/G2/G3 的阻断清单，并保留原始证据。

P0 的计划状态初始为 `PLANNED`。只有在实际执行并归档证据后，才可在 `tasks/todo.md` 中勾选任务；勾选任务不等于完成产品模块。
