# Test365Alm 项目实施计划书

**面向：公司管理层 / 项目投资决策人**  
**版本：V1.0 立项评审稿｜编制日期：2026-09-20｜文档属性：内部项目规划**

## 1. 管理层决策摘要

Test365Alm 拟建设一个独立、自主可维护的企业级应用质量管理平台，对标原 HP / Micro Focus ALM / Quality Center 产品体系。本文以 OpenText AQM 26.1 公开文档及产品功能矩阵作为研究参考，最终交付范围必须在项目启动阶段按实际版本、Edition、扩展、脚本和客户端清单冻结。[R01][R02]

本项目目标不是一个仅包含用例和缺陷的轻量系统，而是覆盖需求、测试设计、执行、缺陷、发布、报表、版本基线、跨项目复用、自动化调度、企业定制、数据迁移与约定兼容能力的完整替代产品。高级扩展、离线执行、BPT、电子签名、AI 辅助及旧生态兼容纳入独立工作包，不以“后续再考虑”消失。

建议采用“长期产品研发、分阶段投入、以验收证据放行”的方式。首轮只批准 6 周预研及范围冻结预算，验证复杂迁移、基线一致性及历史接口/脚本，再决定后续投入。完整目标采用 36 个月规划基线，允许在正式范围冻结后调整为 24～48 个月区间；该周期是团队投入和范围假设下的估算，不是已经承诺的合同交期。

| 决策项 | 建议方案 |
|---|---|
| 产品定位 | 独立 ALM 业务替代产品，明确公布已验证的迁移和兼容矩阵 |
| 首轮审批 | P0：6 周、平均 6 人、含预备费约 54 万元 |
| 首个阶段产品 | 第 6 个月形成核心业务闭环试用版，不宣称完整替代 |
| 企业版目标 | 第 18 个月完成主要企业能力及试点验证 |
| 全量目标 | 第 36 个月完成已冻结范围的逐项验收；未达项不能计完成 |
| 总投入基线 | 618 人月，研发人工 2472 万元；含规划环境/外部费用及 20% 预备费共 3354 万元 |
| GitHub 可见性 | 建议私有仓库；代码公开或开源许可须另行批准 |
| 本次交付性质 | 项目计划、详细实施方案、工作分解及校验工具，不是已完成的软件 |

## 2. 已知条件、规划假设与待决事项

已知条件：项目名为 Test365Alm；目标是完整 ALM 替代方向；需要老板版计划和可以逐步执行的开发方案。尚未获得团队真实编制、内部成本、目标 ALM 实例、原始脚本、生产数据或正式预算。

因此，本计划使用如下假设：采用企业软件研发团队；允许合理复用基础开源组件；优先私有化交付，架构预留多租户；采用 Web 主工作台与独立执行/兼容组件；综合人月成本按人民币 4 万元计算。所有假设均可在 G0 评审前修改，不能视为用户已经同意。

## 3. 立项理由与收益验证方式

本项目潜在价值是形成自主产品、控制定制交付节奏、减少重复实施工作，并建立测试管理与自动化平台之间的统一质量数据体系。上述是商业假设，不是已经实现的收益，也不能在没有真实合同和客户数据的情况下推导确定收入。

在 P0 访谈试点用户，记录现有流程耗时、迁移成本、授权及维护成本；P1/P2 在相同业务流程上复测，区分产品能力改进与人员熟练度变化。投资回报采用公司提供的数据计算，不使用编造的客户数量、售价或增长率。

建议收益模型：三年净收益＝可验证的外部毛利贡献＋可验证的内部效率收益＋可避免的原系统成本－研发投入－新增运维交付成本。内部节省工时只在确实释放或重新利用产能时计入收益，不能重复计算为收入。

| 收益假设 | 验证数据 | 判断方式 |
|---|---|---|
| 需求到测试更易追踪 | 固定场景操作时长、遗漏关系数量 | 试点前后同口径对比 |
| 报表制作减少人工 | 月度报告准备及核对人时 | 对比实际记录，不使用主观满意度替代 |
| 迁移交付可复用 | 每项目迁移工时、失败重跑比例 | 第二、第三项目复用验证 |
| 客户接受完整替代 | 真实试点验收、明确的采购反馈 | 不以演示人数或下载量代替 |
| 产品可持续维护 | 每版本回归成本、线上故障、兼容问题 | 连续版本观察 |

## 4. 产品范围与交付边界

官方产品区分不同 Edition，扩展和云服务也存在差异。因此，范围应以功能及行为清单管理，而不是只以产品名称管理。[R01]

| 范围层 | 本项目包含的目标 | 交付原则 |
|---|---|---|
| 核心闭环 | 发布、需求、测试计划、测试集、运行、缺陷、追踪、报表 | P1 先交付可用闭环 |
| 企业能力 | 动态字段、流程、基线、版本、资产库、模板、跨项目报表 | P2 补齐关键企业使用场景 |
| 执行与集成 | 执行节点、调度、实验室、资源预订、外部连接器 | 固定工具、版本与许可矩阵 |
| 高级能力 | BPT、流程模型、风险规划、离线、电子签名、AI | P3 独立验收，不能被核心闭环替代 |
| 历史生态 | 迁移、REST、OTA/COM、VBScript、客户端与插件 | 按场景验证，不以有 API 代替兼容 |
| 产品化 | 安全、容量、安装升级、备份恢复、支持工具 | P4 全面收敛并验收 |

外部测试引擎的完整自研，例如重建完整 LoadRunner 或 UFT，不包含在 Test365Alm 的基础研发预算中。本项目负责其资产引用、合法调用、调度、结果和追踪；需要自研测试引擎时必须另立项目。AutoPass 等厂商许可系统不能绕过，商业连接器与外部产品使用权单列。

云厂商数据中心服务、24×7 人工支持及第三方认证，不因为做出相同页面就自动具备；如纳入销售承诺，须有对应运营、合同和认证投入。

## 5. 可行性与最大技术风险

需求、测试、缺陷等原生业务能力具备明确的工程实现路径。真正的不确定性集中在历史资产语义、复杂工作流、原有接口行为和旧客户端生态。

官方开发资料分别列出项目 REST、站点管理 REST、基于 COM 的 OTA、站点管理 COM 及自定义测试类型接口，说明兼容工作不是单一的 REST 增删改查。[R02]

本计划采用以下降险措施：第一天设计稳定身份、不可变修订和运行快照；P0 就做复杂数据及脚本验证；兼容层与新业务内核隔离；迁移工具与业务模块同步研发；未通过的兼容项保留在最终阻断清单。

| 风险 | 早期验证 | 不通过时的处理 |
|---|---|---|
| 旧客户端无法直接连接 | P0 真实客户端协议及合法接口验证 | 调整兼容声明与预算，保留差异，不虚报完成 |
| 历史数据无法完整提取 | 三类脱敏项目迁移验证 | 补充合法数据来源、只读存档方案并记录缺口 |
| 基线与历史执行变化 | 并发修改及固定版本测试 | 暂停扩展开发，先修复数据模型 |
| 全量范围不断扩大 | 冻结版本、Edition 和扩展清单 | 正式变更评估，不无限吸收需求 |
| 专项人才不足 | Windows/COM、迁移和领域能力评估 | 提前招聘或引入授权外部支持 |

## 6. 技术路线与组织方式

产品采用模块化业务内核，按需求、测试、运行、缺陷、规则、版本、审计等领域分工；执行节点、外部集成、迁移及 Windows 兼容组件独立部署。此选择是本项目的架构建议，不是原产品内部架构描述。

建议技术方向：React/TypeScript Web 工作台；Java/Spring Boot 后端；PostgreSQL 主数据；对象存储保存附件与证据；Go 或适合团队的受支持运行时实现执行节点；Windows 原生桥接采用经过验证的 .NET/COM 方案。具体版本在 P0 锁定并定期维护。[R05][R06][R07][R14]

避免一开始拆成大量微服务。先保证需求、用例、版本、审计与关系更新的一致性，再按执行隔离、吞吐和发布节奏拆分。不得用复杂基础设施掩盖核心业务模型尚未确定的问题。

## 7. 36 个月里程碑与阶段闸门

计划采用 78 个两周迭代、共 156 周作为 36 个月的近似规划视图；月与周是预算和排期的两种表达，并非精确历月换算。实际日历在启动日期批准后生成，节假日、招聘和外部审批重新计入。

| 阶段 | 迭代 / 周数 | 累计月份 | 核心交付 | 闸门 |
|---|---|---|---|---|
| P0 | S01～S03 / W01～W06 | 1.5 | 范围冻结、样本、三类高风险验证、预算基线 | G0 |
| P1 | S04～S13 / W07～W26 | 6 | 核心业务闭环、基础迁移、内部试用 | G1 |
| P2 | S14～S39 / W27～W78 | 18 | 企业定制、基线、执行调度、模板、企业试点 | G2 |
| P3 | S40～S65 / W79～W130 | 30 | 复杂兼容、高级扩展、完整迁移和差异收敛 | G3 |
| P4 | S66～S78 / W131～W156 | 36 | 全量回归、容量灾备、上线验收与维护移交 | G4 |

G0 放行条件：样本合法可用，范围矩阵可审计，关键风险有验证结果，预算和责任人已确认。G1 放行条件：核心端到端业务完成，历史运行不变，基本权限验证通过；仅允许按明确边界试用。

G2 放行条件：企业场景、迁移演练、规则及基线通过验收，生产试点必须额外满足安全和恢复要求。G3 放行条件：高级能力与兼容子清单逐项有证据，所有未解项有处理计划。G4 放行条件：冻结范围所有 MUST 项通过，无关键安全或数据完整性阻断，发行和运维资料齐备。

任何阶段的“通过率”都不能抵消一个关键未完成项目。例如，99% 页面完成但不能迁移客户关键基线，不满足全量替代验收。

## 10. 工作管理与进度报告

采用两周迭代，每项工作必须关联范围编号、实现任务、测试编号和验收证据。仓库提供 32 个工作模块、192 个工作包级步骤和 160 条模块验收场景，另附端到端场景；这些是初始分解，不是原厂全部功能的完整统计，也不是 192 个小任务可以直接等同于 618 人月。

迭代前将工作包拆成可在数日完成的开发任务，由实际团队估算。工作包计划覆盖设计、开发、测试及集成；预算还包含治理、修复、回归、交付和专项研究，不以未校准的故事点换算人月。

周报只报告已验收功能、关键阻塞、完工预测、实际成本和下一阶段决策。完成文档、完成代码、测试通过、客户验收四种状态分开，不能用代码行数、提交次数或“开发说完成”替代交付结果。

范围变更需描述商业原因、目标行为、涉及数据、接口、测试、迁移和运维的影响，评估增量人月与关键路径，再由变更委员会批准。客户提出的新功能不能悄悄覆盖已冻结的兼容目标。

## 11. 质量、安全与验收指标

候选非功能目标包括参考业务负载下核心交互 API p95 不高于 800ms、错误率低于 0.5%；企业试点恢复目标候选为 RPO 15 分钟、RTO 4 小时。上述数字均为设计和采购评估目标，尚未实现或实测。

数据验收要求：对象去向可解释、关系完整、关键附件哈希一致、历史版本与签名来源真实；权限验收覆盖页面、API、搜索、报表、导出、附件、执行节点、离线同步和 AI 检索。不存在可以接受的跨租户数据泄漏。

发行前必须具备独立构建、安装升级、备份恢复、失败重试、已知差异和支持移交证据。电子签名功能不等于自动符合某个监管制度，需要结合企业适用规则与实际验证另行确认。

## 12. 风险升级与调整规则

建议设置三类决策。继续：本阶段目标达到，剩余风险在已批准额度内。调整：客户样本揭示重大兼容差异、关键人员未到岗或环境限制影响目标，需要变更范围版本、周期或预算。暂停后续投入：缺乏合法目标环境、关键数据无法取得、重大安全或知识产权问题未解决，先处理阻断再投入大规模开发。

暂停某个兼容工作包不等于放弃全部原生业务研发，但必须将产品阶段性能力与完整目标清楚区分。已知不能验证的能力不得进入宣传、合同和验收“已完成”栏。

## 13. 知识产权、商业授权与数据治理

Test365Alm 应独立设计和实现，使用合法公开资料及获授权测试环境形成行为规范。禁止直接复制专有代码、图标素材、文档或绕过原产品授权。兼容性研究、SDK 再分发、组件标识和商业集成须结合实际许可及适用法律审查；本文不是法律意见。
