三、测试定义、实例、运行与尝试必须分开

采用现有领域模型的逻辑对象：
test_set、test_instance、run_manifest、
run、run_attempt、run_step。

可以增加必要的 manifest_step、结果事件、
执行专属幂等/Outbox 表，但不建设通用调度平台。

固定本轮语义：

1. test_case/test_revision/test_step 继续表示测试定义。
   不能把执行结果写回用例或修改其历史步骤。

2. test_instance 是某测试集内的一项测试任务，
   指向明确的 test_case_id 和已封存 test_revision_id。
   第一版只支持 FIXED 修订，不支持动态 latest。
   页面可以默认选中当前修订，但请求和数据库必须保存明确 ID。

3. 同一测试集中，同一用例的同一修订不得无意重复加入。
   使用唯一约束与幂等行为落实。
   本轮不实现已加入实例的换版、转移或删除；
   新修订可以建立新的明确实例，旧实例保持不变。

4. run 绑定一个测试实例及一个不可变 manifest。
   创建 run 时同时创建第一个 run_attempt。
   run_attempt 的 attempt_no 在同一 run 内唯一递增。

5. 重跑产生新 run_attempt，不清空或重用旧尝试。
   本轮重跑沿用该 run 原来的 manifest。
   要执行另一版用例，应通过相应新实例创建新的 run。

6. 同一 run 同时最多一个未结束尝试。
   重复点击、并发重跑不能产生两个活动尝试。

7. 每一步结果绑定 attempt_id 和 manifest 中的 step_key。
   相同 step_key 出现在另一个用例、manifest 或 attempt，
   不能被拿来修改当前运行。

8. 租户、项目、测试集、实例、用例、修订、
   manifest、run、attempt、step 的归属使用明确复合约束。
   不能仅凭一个 UUID 存在就允许跨范围引用。

manifest 至少包含：

没有实现的字段 schema/工作流平台，

由服务端生成规范化快照与摘要。
关键关系仍通过类型明确的字段/外键约束，

要求：

五、执行状态与测试结论

必须区分：
执行状态：RUNNING、PAUSED、FINISHED。
步骤结论：NOT_RUN、PASS、FAIL、BLOCKED。
尝试结论：未结束时为空；结束时为 PASS/FAIL/BLOCKED。

本轮规则固定：

1. 新尝试为 RUNNING，所有步骤初始 NOT_RUN。
2. RUNNING 可保存步骤、暂停或完成。
3. PAUSED 可读取和继续；不能偷偷写步骤或直接改结果。
4. FINISHED 为终态，不允许继续编辑、暂停或恢复。
5. 还有 NOT_RUN 步骤时拒绝完成。
6. 全部步骤已记录后：
   有 FAIL → FAIL；
   无 FAIL 但有 BLOCKED → BLOCKED；
   全部 PASS → PASS。
7. 最终结论由服务端依据已保存步骤计算，
   不接受客户端任意指定“整体通过”。
8. FAIL/BLOCKED 要求非空实际结果或说明；
   冻结各字段长度与错误码。
9. 保存步骤、修改未结束步骤、暂停、继续、完成、
   重跑都记录真实操作者、时间及版本。
10. 未结束尝试允许修改已填写结果，
    但原值通过追加事件或修订保留，不无痕覆盖。
11. 已结束尝试的步骤集合与结果不可追加、改写或清空。
    完成后的更正流程本轮不实现，接口明确拒绝。

关闭浏览器后，从服务器最近确认的步骤继续。
未提交或结果未知的输入要明确提示，
不能声称尚未实现的离线缓存已同步。
