# Test365Alm 详细实施方案

**面向：架构、产品、后端、前端、测试、迁移、兼容与运维团队**  
**版本：V1.0 立项级执行基线｜日期：2026-09-20**

## 1. 如何使用本方案

本方案提供从范围调查、工程建立、领域开发到迁移、全量验收和维护的实施顺序。执行时先读第 2～10 章建立统一约束，再按 planning/sprints.csv 的迭代安排和附录 32 个模块手册开发。每个模块包含前置条件、实体、接口、六个工作包级步骤及五条验收场景。

当前交付是详细研发方案与项目资产，不是完整应用代码。tools 中的文档校验和预算计算可以现在运行；应用启动、业务 API、迁移和旧生态兼容需要依照方案实际开发。不得把示例契约、空目录或自动生成的样例当作已完成功能。

ALM 目标实例、Edition、扩展、旧脚本及生产数据尚未提供。采用 26.1 官方资料作为参考基线，P0 必须建立实际产品的完整功能盘点；未确定项不能在最终全量验收时被默认排除。[R01][R02]

本方案中的开发步骤是工作包，不是几条命令自动生成企业产品。一个工作包应拆为数日内可完成的 Issue，落实实现提交、自动化测试及真实业务证据。仓库内测试场景初始状态均为 NOT_RUN，避免文档生成后产生虚假的完成率。

## 2. 目标、约束与“完成”的定义

最终目标分成七张独立验收表：业务功能、历史数据、项目 REST、站点管理与 OTA/COM、工作流脚本、客户端/扩展、非功能与交付。只有已冻结范围内全部 MUST 项有证据且关键差异关闭，才可声明全量替代完成。

原生业务能力与历史兼容并行建设。新业务 API 可采用现代设计；旧接口的反腐层保存旧语义，并通过统一业务服务执行权限、规则和审计。任何兼容适配器不得直接绕过业务内核写库。

“相同业务目的”“相同数据含义”“相同 API 行为”“相同旧客户端可运行”是不同层次。基线、脚本和 COM 的特定语义以官方资料和合法实机样本验证，不通过名称相似推定完成。[R02][R03][R04]

范围排除仅限明确独立产品：重新实现完整 UFT、LoadRunner 等执行引擎；本项目仍需实现已冻结的调用、调度和结果集成。任何将原 ALM 服务端继续作为底层的过渡功能，必须标注“共存”，不能计为独立替代完成。

## 3. 总体架构与模块边界

```text
浏览器工作台 / 离线客户端 / 外部业务调用
                  |
          HTTPS / 身份代理 / BFF
                  |
        Test365Alm 模块化业务内核
  项目  元数据  需求  测试  运行  缺陷  追踪
  规则  版本基线  审计  资产  报表  项目规划
         |                |             |
   事务 Outbox       异步工作进程     原生 API
         |                |             |
   集成连接器       执行调度器      独立兼容网关
                         |             |
                Windows/Linux节点   REST/COM/脚本
                         |
                合法授权的测试引擎
```

业务内核先做模块化单体，所有模块通过显式 application service 或领域事件交互。执行节点、兼容进程及高耗时工作进程独立，避免脚本和测试引擎崩溃影响交易服务。

模块内部采用 domain、application、infrastructure、interfaces 分层。业务规则放在 domain/application；HTTP Controller 只做协议转换，不能把所有规则堆在 Controller。公共包只放稳定的身份、时间、错误及事件协议，不建立无边界的 shared-business 巨包。

数据库是交易事实来源；搜索索引、仪表盘和统计为可重建投影。对象存储是文件内容来源，但元数据、引用、保留和可用状态仍由业务服务管理。跨系统调用不进入数据库长事务。

## 6. P0 前六周逐周执行安排

### 第 1 周：建立授权、范围与共同语言

产品负责人收集目标版本及扩展清单，领域专家录制业务主线，项目经理建立 D01～D08 决策表。架构师组织对象建模，明确 Requirement、Test、Instance、Run、Attempt、Baseline 的区别。安全负责人完成数据使用授权和脱敏规则。

本周产出：目标环境登记、初始范围矩阵、术语表、角色名单、样本审批和威胁模型。验收：每个核心业务名词有定义，任何未知兼容项被登记，不把猜测写成客户事实。

### 第 2 周：搭建工程与核心风险样本

建立开发分支和自动化文档检查；使用官方初始化工具生成候选后端与前端，提交依赖锁。准备普通、强定制和大容量三类脱敏项目。记录原 REST、OTA、VBScript 以及基线固定行为的请求与结果。

本周产出：可构建健康检查、版本锁草案、黄金数据清单、接口及脚本轨迹。验收：新开发机可复现构建，样本哈希和来源清楚，实际未验证项保持 OPEN。

### 第 3 周：验证一致性与迁移通道

实现仅用于研究的最小版本/基线模型；并发修改用例和关系时建立快照，证明不会混合不同版本。编写只读样本提取和中间格式转换，验证附件、作者、时区和历史修订可取得程度。

本周产出：基线概念验证、数据缺口报告、迁移映射草案。验收：重复导入不增加对象，无法提取的数据逐项标记；概念验证不计为完整产品实现。

### 第 4 周：验证兼容可行性

前端可按 Vite 官方脚手架生成，第一次允许解析当前脚手架，生成后立即检查并提交锁文件；后续 CI 不重复执行 latest。[R15]

```bash

cd apps/web

# 提交 package.json 与 package-lock.json 后，CI 使用 npm ci
```

### 7.2 第一条纵向切片

先实现“已登录的项目测试人员创建一条需求”。数据库迁移创建项目、成员和需求身份/修订；API 校验主体与项目；表单按元数据显示；保存写入版本、审计和 outbox；列表读取带项目过滤；QA 验证未授权访问和并发冲突。

第二条切片实现“需求关联测试”；第三条实现“测试实例手工运行”；第四条实现“失败步骤创建缺陷并复测”。每条切片必须包括界面、接口、数据库、权限、审计及测试，不先批量画完所有页面再补后端。

### 7.3 每个业务命令的标准开发顺序

第一步写验收场景和命令契约；第二步写数据迁移及约束；第三步写领域规则和失败分支单测；第四步实现应用事务；第五步接入 API 和页面；第六步加入真实数据库集成、权限负向、并发及端到端测试；第七步独立评审并保存证据。

模块手册中的“六步”描述业务研发工作包，此处“七步”是每个命令的统一实现纪律，两者不是互相替代。

## 8. 数据模型与不可破坏的不变量

### 8.1 核心关系

```text
Tenant -> Domain -> Project -> Membership
Project -> Requirement -> RequirementRevision
Project -> TestCase -> TestRevision -> TestStep
TestCase -> TestConfiguration
TestSet -> TestInstance -> Run -> RunAttempt -> RunStep
Baseline -> BaselineMember -> EntityRevision
TraceLink -> 两端稳定实体身份 + 关系修订
Asset -> AssetRevision -> 对象存储版本
Signature -> 对象修订 + 资产清单哈希 + 策略版本
```

稳定身份用于关联，修订用于描述某一时刻的内容。当前指针可以变化，已发布修订不可原地覆盖。逻辑删除不能级联删除历史运行、签名和基线。所有统计必须知道自己使用的是当前状态、某基线还是某次运行快照。

### 8.2 所有业务表的约定

项目内实体保存 tenant_id、project_id、id、created_at、created_by 及 row_version。事件时间使用 timestamptz/UTC；仅表示日历日期的字段使用 date。用户输入的金额或精度敏感数字用定点数，不使用二进制浮点承载精确业务值。

复合外键应包含 tenant_id、project_id，以防引用其他租户/项目。跨项目共享使用专门授权映射，不删除复合约束来“方便关联”。历史作者使用稳定 principal，用户离职后保留必要身份映射。

### 8.3 二十项设计不变量

1. 一个业务实体只有一个稳定身份，修改产生新修订或受审计状态事件。
2. 运行必须引用已解析的 manifest，不能在每次展示时读取当前用例。
3. 重跑保留旧 attempt，不复用并覆盖旧结果。
4. 同一有效租约只能有一个 fencing_token，可识别过期节点。
5. 一个幂等键在同主体、项目、命令范围内只代表同一请求内容。
6. 权限同时约束读取、统计、搜索、导出、附件、任务和 AI。
7. 业务写入、审计意图与 outbox 在同一数据库事务中提交。
8. 外部调用不在持有业务锁的长事务内执行。
9. 基线 READY 之前必须验证全部成员、关系和资源版本。
10. 被保留锁、基线或有效签名引用的证据不能普通物理删除。
11. 关系两端真实存在且具备允许的类型与作用域。
12. 自定义字段类型和校验对 UI、API、导入及兼容入口一致。
13. 规则版本固定，变更不会重写已运行流程的历史解释。
14. 报表附统计口径、数据水位和范围，避免将缓存当作最新事实。
15. 跨项目同步使用来源映射，不能共享同一可变行充当复制。
16. 迁移源时间、源身份、源签名与迁入时间分开记录。
17. 所有关键删除均有影响预览、权限和保留审查。
18. 未知外部副作用不能因网络超时自动盲目重试。
19. 业务错误、基础设施错误和未确定结果必须可区分。
20. 完整兼容和全量完成声明只由测试证据支持，不能由界面或文档数量推断。

详细表清单及字段设计见 contracts/domain-model.md。它是研发设计依据，不能直接作为未经校验的生产建库脚本。

## 9. API、错误码、权限与幂等协议

### 9.1 原生 API 约定

项目资源统一使用 /api/v1/projects/{projectId}/...；站点级接口使用 /api/v1/admin/...；节点接口独立认证。列表采用稳定 cursor 或明确的 page/size，排序包含稳定 ID 作为最后的并列键；大导出使用快照任务而不是反复翻页抓最新数据。

写入创建命令使用 Idempotency-Key；更新使用 If-Match 对应 row_version。列表默认 limit 50、最大 200 为建议值，可经容量测试调整。响应包含 requestId；异步创建返回 jobId 和状态查询位置，不能在任务尚未完成时返回业务“成功”。

典型错误：401 未认证；403 已识别主体但无操作权限；对需要隐藏资源存在性的场景统一 404；409 状态或幂等内容冲突；412 版本不匹配；422 业务输入无效；429 限流；503 暂不可用。错误体使用固定 code、message、details、requestId，不返回 SQL 或内部堆栈。

### 9.2 幂等键处理

键范围为 tenant、project、principal、command_type、key；请求体规范化后保存 SHA-256。第一次请求插入占位记录，业务事务成功后保存结果引用；相同键相同内容返回既有结果，相同键不同内容返回 409。处理中记录设定租约，崩溃后按持久化结果恢复，不能只在内存缓存去重。

对资源版本、运行创建、从失败步骤创建缺陷和迁移导入使用持久业务唯一约束，幂等键过期后仍能避免不可接受的重复。一般查询无须幂等存储；外部邮件、支付等副作用需要外部幂等能力或人工核对，不能靠本站的幂等键单方面保证。

### 9.3 标准写事务伪代码

```text
authenticate(); authorize(project, action, resource)
validate command and field schema
begin transaction
  establish verified tenant/project context
  reserve idempotency key or return prior result
  load aggregate and check expected version
  apply domain and workflow rules
  persist new revision / state transition
  append audit intent and outbox event
  save idempotency result reference
commit
return stable result with new ETag
```

拒绝和失败的安全审计可走独立受限通道，避免业务事务回滚后完全没有失败证据。成功业务审计与写入需保持一致；审计通道本身不能引入敏感数据泄露。

### 9.4 契约文件使用方式

contracts/openapi-core.json 是 OpenAPI 3.1 核心纵向切片的契约种子；覆盖的 operationId 可机器校验。planning/api-catalogue.csv 列出更广的拟定接口。未在核心契约中的接口按模块手册补充请求字段、响应、权限、错误和测试后，才能进入开发。该文件不是原 ALM 全量 API 规范。[R13]

## 10. 六条核心状态机

| 对象 | 合法状态及关键转换 | 不允许的捷径 |
|---|---|---|
| 需求修订 | DRAFT → IN_REVIEW → APPROVED；驳回生成修改过程 | 修改 APPROVED 原文但保持原签批 |
| 缺陷 | NEW → TRIAGED → IN_PROGRESS → RESOLVED → VERIFIED → CLOSED；允许按规则 REOPENED | 无修复说明或权限直接关闭 |
| 执行任务 | QUEUED → LEASED → RUNNING → FINISHED；可转 CANCELLED/EXPIRED | 过期节点覆盖有效新 attempt |
| 运行结论 | NOT_EVALUATED/PASS/FAIL/BLOCKED/ERROR 等，与执行状态分离 | 将节点故障当作测试断言失败 |
| 基线 | DRAFT → CAPTURING → VALIDATING → READY；失败转 FAILED | 尚缺附件的基线参与签名或执行 |
| 迁移批次 | EXTRACTED → VALIDATED → LOADED → RECONCILED；异常 QUARANTINED | 未提交目标数据就推进检查点 |

各状态转换都保存操作者、原因、时间、原状态、新状态及规则版本。节点结果和用户更正不能混用同一接口；已结束运行的更正必须为追加事件。

## 11. 关键算法一：建立一致基线

第一步检查创建权限、库范围和源对象状态。第二步在数据库一致性快照中计算依赖闭包，收集实体修订、关系修订及资源版本，并冻结 manifest。第三步提交基线草稿和清单；后续不再读取“最新”替代任何条目。

第四步异步验证所有对象版本可读、哈希一致且满足保留策略；为必要依赖建立引用保留。第五步清单验证全部通过才进入 READY；任何缺项进入 FAILED 并显示可修复原因。第六步通过并发更新、附件删除、任务重试及数据库恢复场景验收。

大基线不能长时间持有影响生产的事务。可选方案为在一致快照中快速固定身份/修订清单，再异步打包；更大规模方案需评估快照日志或导出机制，并在 ADR 写清 MVCC 保留和运维成本。

官方基线还包含实体关系以及运行所需的库外依赖，因此“给当前数据打一个标签”不足以实现该能力。[R03]

## 12. 关键算法二：租约、重试与结果回传

领取任务在数据库事务内使用原子条件更新或受控 SKIP LOCKED；只有从可领取状态成功转换的节点获得 lease_id、expiry 和 fencing_token。节点心跳延长当前租约，但已经进入终态的任务不可被迟到心跳复活。

结果回传键为 attempt_id、chunk_sequence，重复块需相同哈希；同序号不同内容进入冲突。节点发送完成标记后，服务端检查必要结果和证据完整性再结束 attempt。

租约过期并不必然意味着外部测试从未运行。只有确认任务可安全重试，才新建 attempt；存在未知外部副作用时进入 UNKNOWN/人工核对。旧 attempt 的迟到结果可作为隔离证据保留，但不能替换有效结论。

取消任务先变更取消意图，再通知节点，并设置最终取消期限；超时无法确认则隔离执行节点或资源并告警。禁止在未停止旧进程时将独占设备重新分配给其他任务。

## 13. 关键算法三：流程、事件与跨项目合并

新规则按确定顺序执行：主体权限、字段 schema、命令前置条件、领域规则、状态转换、事务写入、异步动作意图。表单规则只是交互便利，不能授权或替代服务端规则。

Outbox 消费采用至少一次处理，每个消费者使用 event_id 唯一约束；消费者与其业务结果在同一事务提交。失败指数退避，达到上限进入死信队列；人工重放仍受幂等约束。

模板和资产复用采用三方合并：基准为上次同步版本，分别比较源与目标。仅一侧改变可以安全继承；两侧同字段改变进入冲突；删除与修改冲突不能默认删除。合并完成生成新本地修订，保存来源映射。

旧脚本模式需要精确验证模板和项目事件次序，其行为不一定与新规则执行顺序相同。[R04] 将旧兼容模式隔离，避免为了模拟历史副作用污染原生事务设计。

## 14. 数据迁移、共存与切换手册

### 14.1 提取与规范中间格式

每个对象记录源系统、项目、实体类型、源 ID、源修订、源时间、原作者、payload、关系和附件清单。二进制文件另存并计算哈希；中间格式标注 schema_version，不能只保存容易失去类型信息的自由 Excel。

授权接口覆盖不足时先记录缺口，评估官方导出、受许可的只读提取或保留旧证据库。不能直接改原系统数据库，也不能在没有证据时虚构历史签名或字段。

### 14.2 导入顺序和恢复点

先建元数据、项目与身份映射；再建稳定身份；然后导入修订、资源和关系；再导入测试实例、运行、步骤、基线及来源证据。每批目标事务提交后更新检查点。目标提交成功但检查点失败时安全重放，依赖唯一映射保证不重复。

对失败对象进入隔离区并保留原始输入、错误码、尝试次数和修复记录。批次报告区分已成功、隔离、保留旧系统和明确不支持四种去向；不得无提示丢弃。

### 14.3 增量同步

源有可靠变更日志时按官方支持方式读取；仅有更新时间时使用时间加 ID 水位和重叠窗口，并定期全量核对删除、关系变化和未更新时间的内容。时间戳不能被默认视为完整 CDC。

共存期每种对象规定唯一写入权威，双向同步必须定义字段主权和冲突处理。避免两端都可自由修改而没有冲突队列。

### 14.4 切换检查清单

切换前：两次恢复及迁移演练完成；范围和差异签字；备份可恢复；支持人员就位。切换中：原系统停写、排空正在运行任务、执行最后增量、冻结源水位、数量/哈希/关系/指标对账、业务抽样确认。切换后：限定人群放量、观察告警、记录新写入水位、再扩大使用范围。

回滚触发建议：关键数据缺失、越权、安全事件或核心业务无法恢复。回滚先停新写入并保全日志，不能直接把上线后数据抹掉；若缺乏反向迁移，采用冻结新写入、修复前滚或保留差异重放策略，必须由业务批准。

## 15. 旧生态兼容实验室

建立隔离 Windows VM，按目标版本与位数分别安装合法原客户端、SDK 和依赖。保存快照、安装包哈希及授权记录，不在公司生产电脑替换 COM 注册项。样本分组包括 OTA 工具、站点管理工具、VBScript、Excel 宏、自定义测试类型、第三方插件及原客户端。

REST 差分测试比较状态码、头、Cookie、字段类型、分页、空值、时间、错误和真实持久化结果。COM 差分测试另外比较对象身份、枚举、可选参数、事件、提交、刷新、锁与错误语义。对随机 ID、时间等非确定字段需要受控规范化，不得把业务差异一并过滤掉。

记录 unsupported 行为并明确原生替代路径；兼容声明分为 zero-change、requires-config、requires-code-change、unsupported、not-tested。只有第一类可宣传零修改，且必须关联原样本执行结果。

公开 API 文档不自动覆盖厂商原客户端通信；没有合法实现路径或样本证据的项目进入 G0/G3 风险决策，不能用一份“兼容接口”文件宣告完成。[R02]

## 16. 测试策略与质量闸门

### 16.1 分层测试

单元测试覆盖领域规则、状态转换、参数解析、幂等和冲突判定。集成测试使用真实 PostgreSQL 与对象存储替身/受控实例，重点验证事务、约束、RLS 和 Flyway。契约测试校验原生与旧接口；E2E 测试覆盖角色操作和业务闭环；兼容测试使用原样本；性能和安全单独环境验证。

不要用内存数据库通过来代替 PostgreSQL 的 RLS、锁、JSONB 或并发测试。自动化测试要包含时区、长文本、中文、空值、极端树深、重复回传、断网和恢复。

### 16.2 建议流水线门禁

PR 阶段：格式、类型、单元、架构、迁移、契约和基本权限测试必须通过。夜间：完整集成、E2E、扫描、迁移回归和主要兼容样本。发行候选：全量场景、容量、长稳、灾备、升级和真实业务 UAT。

覆盖率仅作辅助阈值，候选为核心领域行覆盖不低于 80%、关键状态转换 100% 场景覆盖；最终阈值以测试价值审查为准。无论覆盖率多少，缺少租户隔离或历史证据保护测试都不能放行。

### 16.3 完成定义

业务任务完成至少具备：范围 ID、设计/ADR、实现提交、数据库迁移、API 契约、权限说明、成功与失败测试、审计、文档、监控、兼容/迁移影响和验收人。涉及 UI 时补充加载、空、错误、只读和无权状态；涉及删除时补充保留引用检查。

planning/acceptance-cases.csv 的 NOT_RUN 只能在实际运行并保存证据后改为 PASSED/FAILED。文档校验通过不意味着这些产品测试通过。

## 17. 非功能目标与容量测试方法

候选参考数据集：100 个项目、20 万需求、100 万用例、1000 万运行步骤及 1 TB 附件；这些是设计验证档，不是来自用户账户的数据。起始交互负载为 100 活跃用户、约 50 RPS；实际思考时间及业务配比必须由脚本和报告固定。

建议业务配比：列表/详情 60%、搜索/筛选 15%、业务写入 15%、运行结果及轻量附件元数据 10%；大附件、导出、基线及迁移作为独立背景负载。所有压测只对明确授权的目标进行，执行节点限制目的地址和最大并发。

参考部署：2 个 8 vCPU/16 GB 应用实例、1 个 4 vCPU/8 GB 工作进程、16 vCPU/64 GB 级交易数据库和受支持的对象存储，仅为初始测试环境假设。最终采购必须依据基准测试和可用性要求，不把该规格直接写成容量保证。

测量 p50/p95/p99、错误率、数据库锁等待、连接池、CPU、内存、GC、队列延迟、执行机利用率和投影水位。缓存预热与冷启动分开，单次峰值与长稳分开，不仅展示平均响应时间。

可用性候选目标 99.9% 只有在定义统计窗口、探测方式、维护窗口和责任边界后才可用于 SLA。恢复候选 RPO 15 分钟/RTO 4 小时必须用实际日志、对象版本和恢复演练确认，不能只配置定时备份就宣称达成。

## 18. 安全、隐私与证据保护

身份由成熟提供方承担认证，应用负责具体资源授权。浏览器不长期把高权限令牌存入 localStorage；BFF Cookie 配置 Secure、HttpOnly、SameSite 并落实 CSRF。服务账户按项目和动作最小授权，执行节点不得使用站点管理员凭据。

脚本、插件和测试引擎属于高风险执行边界；采用受限账户、工作目录、网络访问和进程隔离。附件扫描失败即隔离；URL 导入控制 SSRF；Webhook 验签与去重；Excel 导出防公式注入；富文本双层净化。

RLS 作为第二道防线，应验证表 owner、superuser 和 BYPASSRLS 绕过规则，应用不能用这些账户连接。[R08] 无项目上下文时默认拒绝而非查询全部项目。所有 SQL 必须参数化，元数据过滤不转成任意字符串 SQL。

审计记录保留操作者、动作、对象修订、原因和 requestId；敏感字段只保存必要摘要或受控加密值。可信保留需数据库外的独立边界，哈希链不能单独对抗拥有全库控制权的攻击者。

AI 检索按权限过滤，输出只进入草稿；电子签名绑定修订及策略，不能把历史导入记录伪装成当年本站签署；离线撤权不能保证断网设备即时擦除既有缓存。这些边界必须进入产品说明与验收。

## 19. 部署、升级、备份与故障响应

环境至少区分 dev、integration、staging、production；配置和密钥分离；镜像与安装包按摘要部署。生产变更来自受审批发行候选，不在服务器临时修改代码。数据库迁移由独立账户执行，应用运行账户无 DDL 权限。

发布顺序：验证备份和回滚前提；执行兼容扩展迁移；部署新版本少量实例；健康与业务冒烟；逐步切换；执行受控回填；确认旧版本退出后再安排破坏性收缩。不可逆数据转换优先前滚修复，不能承诺任何时候都能简单回退二进制。

备份覆盖数据库、对象版本、配置、密钥恢复材料和发行清单，分别规定访问人和保留周期。每月建议至少一次隔离恢复演练，重大升级前额外演练；不要将备份成功日志等同于恢复成功。

故障分级建议：S1 数据泄漏/核心不可用，立即升级；S2 主要流程受阻，限制影响并恢复；S3 局部功能问题，进入计划修复。具体响应时限按公司值班和客户合同批准，不在未建立支持团队时承诺 24×7。

## 20. 迭代、依赖与任务执行规则

planning/sprints.csv 提供 78 个两周迭代的焦点和出口。模块依赖描述最终完整模块的依赖，不意味着必须等依赖模块所有高级能力完成才做初级切片；各迭代通过已冻结的接口与最小可用能力推进。P0 概念验证独立于生产模块实现，不能提前计为模块完成。

为避免依赖误解，每次迭代计划需将“依赖什么具体接口/修订/功能”写到 Issue，而不只写 Mxx。例如手工执行需要可固定的基础测试修订，不需要等待 BPT 或全部跨项目复用；企业试点上线必须等安全与恢复验收，不可用内部试用出口代替。

标准 Issue 包含背景、范围 ID、输入样本、具体依赖、目标行为、不包含项、API/数据库/UI 变更、错误分支、测试 ID、迁移影响、监控、验收证据和回退策略。每次 PR 尽量一个业务目的，数据库迁移与应用变更配套审查。

所有初始任务为 PLANNED；未指定真实 GitHub 用户的角色不能直接当作已分派负责人。本次文件包没有自动创建 192 个远端 Issue，避免未经用户确认的大量通知和虚假的项目执行状态。

## 21. 全量验收和发行清单

G4 逐项核对：签批范围、实现版本、测试记录、客户样本、权限负向、迁移去向、兼容差异、容量、安全、恢复及培训。验收人必须能重现重要结果，而不是仅收到一段描述性周报。

发行包至少含：源代码及依赖锁、构建镜像/安装器、数据库迁移、前端静态资源、执行节点、兼容安装包、接口文档、运维和用户手册、SBOM、签名/校验清单、已知差异、迁移工具、验收报告及维护计划。按授权决定哪些内容可以公开。

工具的最终检查规则：任何 MUST 项仍为 PLANNED/BLOCKED/NOT_RUN、证据链接为空或关键差异未批准，即不得生成“全量通过”结论。允许发布阶段版本，但版本说明须诚实列出未实现和不兼容部分。

## 22. 常见返工陷阱与禁止做法

不要把 Test、Instance 和 Run 放成同一可变对象；不要让修改用例改变历史结果；不要用字符串关系绕开租户约束；不要在导出和报表遗漏权限；不要靠定时任务加标签实现一致基线；不要把语法转换当 VBScript 兼容；不要认为 HTTP 网关即可让 OTA 宏零修改；不要让通用规则运行任意命令。

不要用源数据库更新时间当完整增量事实；不要为了便于迁移把历史作者和签名统一改成管理员；不要创建一个空 Docker Compose 文件就宣称可部署；不要写出工作流 YAML 就声称 GitHub 分支保护已经设置；不要用工具校验文档成功冒充业务软件测试成功。

## 23. 角色交接与开发完成后的持续工作

产品团队交付签批范围、行为样本和差异决策；架构团队交付数据/API/事件/ADR；开发交付实现及测试；QA 交付独立验证和证据；迁移团队交付映射、检查点及对账；兼容团队交付真实旧样本结果；SRE 交付安装、恢复、告警和故障演练；业务交付 UAT 签字。

维护按依赖支持周期和客户兼容矩阵持续更新。厂商发布新 ALM 版本或新增扩展时建立新的目标基线，不追溯性地把新范围算作旧版本漏项。数据保留、签名验证和重大安全修复是长期责任，需要年度编制和预算。
