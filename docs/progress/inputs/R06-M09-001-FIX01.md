二、先修多步骤版本与实际 HTTP 契约

当前不一致：
TestExecutionPanel.saveStep 提交 selectedAttempt.rowVersion；
testExecution.ts 没有保留 RunStep.rowVersion；
ExecutionService.saveStep 却比较 run_step.row_version。
第一步成功后，第二步会使用错误版本。

采用单一、明确的版本方案：

1. 最小方案是保留步骤版本：
   前端解析并提交目标步骤自己的 rowVersion；
   暂停、继续、完成使用尝试版本。
   也可统一成尝试级 CAS，但服务、响应、契约和页面必须全部一致。
   不允许混用或靠写死版本通过。

2. 从实际服务响应获取必须的版本。
   缺少版本应拒绝操作，不能默认填 1。

3. If-Match 与 JSON expectedVersion 同时出现时必须一致，
   不能以 JSON 优先而忽略冲突请求头。
   统一缺失、畸形、溢出和陈旧版本的结构化错误。

4. 先验证至少两步：
   保存第一步→保存第二步→修改第一步→暂停→继续→完成。
   经过真实 HTTP、安全过滤器和 runtime 数据源，
   不能只直接调用 Service 或 mock API 成功。

5. 保存步骤与完成协调同一尝试的事务锁/版本。
   完成先提交后，新的步骤写入必须被拒绝；
   步骤先提交，完成必须依据确认后的结果和版本。
   锁顺序一致，数据库死锁不能当作正确业务拒绝。

6. 暂停不能写步骤，终态不能重新修改。
   FAIL/BLOCKED 的说明及长度在 HTTP/服务边界明确验证，
   不把数据库 CHECK 异常当作正常输入错误。

7. 重跑接口也落实已冻结的请求体边界。
   未支持字段、错误 JSON 类型、冲突别名明确拒绝。
   不通过放宽 If-Match、CSRF 或状态检查解决问题。

三、补齐数据库快照、终态与归属保护

当前 V12 对新表主要检查项目成员/writer，
没有完整限制已提交 manifest 追加和终态写入。
V13 只补了幂等清理权限。

先用真实临时 PostgreSQL 复现，再通过新增迁移修复。
不改写已执行 V1—V13，不清库或重造历史。
正式版本增加后同步调整故意失败迁移编号。

必须实现：

1. manifest 及其步骤只在受控构建事务中完整写入。
   提交后不能追加、更新、删除、清空或换内容。
   可以沿用合适的封存机制，但不能让 runtime 任意重新打开。

2. 已结束 run_attempt 不能改回 RUNNING/PAUSED，
   已结束步骤不能修改、补入或删除。
   最终事件允许随完成事务原子写入；
   不允许在终态已经提交后再伪造新的结果变更事件。

3. execution_run 与 run_attempt 的状态不要混淆：
   合法重跑可以更新 run 的当前执行状态，
   但只能新建 attempt，不能重新打开原 FINISHED attempt。

4. run_step 必须属于本 attempt 所绑定 manifest 的步骤。
   事件中的 attempt 必须属于同一个 run。
   manifest 的源修订必须对应所选实例，
   run 的实例与 manifest 必须一致。
   使用复合外键、受控写路径或等效可验证约束，
   不能只分别证明这些 UUID 位于同一个项目。

5. 操作者稳定 ID、版本正数、状态与结论/完成时间组合
   具有必要约束，不允许不可解释的半完成数据提交。

6. 固定合法 MEMBER 的 runtime 上下文，
   直接尝试向已保存 manifest/已结束 attempt 插入数据，
   修改终态结果或跨同项目对象错误关联。
   断言具体拒绝原因和无副作用。
   不用 VIEWER、错误外键或 owner 操作代替合法 writer 负向测试。

7. 运行创建时再次确认固定修订可执行且已封存。
   正常启动、暂停、继续、完成和重跑必须保持可用。

8. manifest 摘要采用无歧义的规范化编码，
   包含完整执行内容及实际格式/规则版本。
   当前将步骤字段用“|”拼接后再整体编码，
   action="open|confirm", expected="done"
   与 action="open", expected="confirm|done" 会得到同一内部串。
   修复编码并增加隔离变量测试，不归咎于 SHA-256。

9. 已有快照和历史不能被静默重算改写。
   必要时给新格式版本明确标识；
   对无法恢复的信息如实保留，不伪造旧数据。

五、端到端幂等：原操作结果与新操作分开

2. 同键同内容返回原操作确认的冻结结果，

   前端后续 GET 失败时区分“写入已成功”和“读取失败”，
   不能盲目重发写请求。
